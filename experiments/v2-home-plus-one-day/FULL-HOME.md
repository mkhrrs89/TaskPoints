# Full Home acceptance for V2-owned Task actions

The full synthetic Home page keeps showing the acknowledged V2 Task date through
reload, Notes navigation, lifecycle refresh, ordinary Save, Task journal
compaction, verified-secondary maintenance, and Chromium restart. Unrelated
data continues through the existing V1 paths. The [Inbox preservation fix](INBOX-STARTUP-LOSS.md)
adds a notification generated by the real Inbox to the same acceptance fixture.

## Title edits

The existing Home Edit and Save controls trim the title and keep the prior
title for blank input. Save uses the Task revision that was visible when
Edit opened, so a refresh can keep the draft without letting it overwrite
a competing edit.

V2 commits the title, update timestamp, and receipt together. The editor
closes after verified readback. Retrying the same unconfirmed save reuses
its receipt ID and title. Reopening verifies that a title receipt changed
only the title and timestamp. Ordinary Home saves still use the V1 backing
state, and the existing detached rollback checkpoint carries the verified
title and date into a fresh V1 profile.

## Importance and Tags

The selected synthetic Task uses the same Home editor for Importance and
Tags. The dropdown keeps its four existing choices. The tag input splits
on commas, trims whitespace, drops empty entries, and keeps order, case,
and duplicates. Clearing the input removes existing tags. Tags with
quotes and angle brackets display as literal text in both editors.

One Save commits the changed fields and any title change in a single V2
receipt. Startup verifies that receipt against the previous Task and
checks that every unrelated field is unchanged. A retry after an
unconfirmed save must use the same fields. Title-only receipts keep their
existing format. Direct Due Date editing and Repeat (including its
custom count and unit) remain V1 fields and are read-only on the
selected synthetic Task.

The browser tests exercise the Home card, Work tag styling, and the
phone-width Critical Tasks indicator. They verify legacy save and
compaction, maintenance, Chromium restart, and a fresh V1 rollback that
keeps the latest fields, a pending unrelated Task journal, Inbox and
other app records, unknown fields, and image bytes.

## Points and earned rewards

The same Home Points input keeps V1's numeric conversion. Blank input
saves zero, and the editor accepts negative, decimal, and exponent
values. V2 admits only finite numbers. A single receipt can commit
Points with any changes to Title, Importance, and Tags.

The legacy Done action copies the Task's points into a completion.
Scoring totals use that stored completion value. A Points edit changes
only the Task row and receipt, leaving completed rewards, Game and
Gold records, and backup bytes intact. The history test uses an actual
recurring completion and a completed one-off Task. It checks that the
past day's total stays at 8 points and that a later completion earns
12.75 points after restart and verified rollback into a fresh V1
profile.

Home refuses legacy Done for the selected synthetic Task while V2
owns it. The legacy path would otherwise award from the stale V1
Task. The existing Done flow is available in the fresh V1 profile
after rollback. Completing a Task while V2 owns it needs a separate
implementation.

## Done ownership checkpoint

Home Done normally captures the Task's current Points in a completion,
checks for a completion on the same local day, and updates the Task and
completion together in the legacy journal. It closes one-off Tasks.
Recurring Tasks advance from their current due date using the existing
recurrence rules and reset their postponement count. The action also
shows the Points toast, updates the Today list and Critical Tasks
indicator, and animates the card. Home's live score and matchup
calculations read completions from the legacy state.

Commit `31bc2d20` preserves the browser witness for the original bug.
After Home changed Points from 5 to 12.75, a newly opened Today page
awarded 5 through its own `saveStateSnapshot` path.

Home and Today now call the same check in the shipped scoring core before
either completion handler can mutate state, award Points, save a
snapshot, journal a completion, or update the Today list. This check
reserves only synthetic Task `t1` on a loopback origin with the ownership
marker. It reads the marker at the point of use, treats malformed bytes
as a hold, and retains a hold for the lifetime of a document that saw
the marker. The old Home owner check remains as a fallback.

The browser tests exercise both controls with an already-open Today tab
and a fresh Today tab. The app loads the shared scoring core in both,
including the root Today URL with the bare core. Neither tab needs the
injected Home owner or synthetic runtime flag to refuse. Repeated
concurrent attempts preserve the stored Tasks, completions, scores,
journals, backups, and Today list. The test also checks a Chromium restart
with malformed marker bytes, marker loss in a loaded document, an
unrelated Task completion, and a fresh detached V1 rollback that awards
12.75 once through the normal Today control. That last award is V1.

The shared check covers the current Home and Today code. An older build
without the check can still write. A new document after loss of the
marker cannot distinguish marker loss from a fresh V1 profile. Keep the
old-client and controlled handoff requirements open.

V2 Done remains paused. Home's `computeTodayPoints` and the canonical
`syncYouMatchups` pipeline still consume V1 completion totals. Before a
V2 award can be enabled, the score display and persisted matchup
calculations must use the same verified completion set and defer writes
when verification fails. Showing only the correct Home total could leave
a persisted Game result calculated from stale rewards. An eventual V2
transaction must commit the Task, completion, and receipt together and
enforce one award per Task and local day inside that transaction.

Today-list state lives in a separate localStorage record. The completion
receipt can supply the Task ID, local day, and initiating control for
reconciliation after commit or restart. The Today checkbox should be
derived from the verified completion. Any persisted list cleanup should
use the latest day map and remove only the affected Task ID and its
order entry, leaving other order entries, notes, and habits intact.
Removing the same entry again is harmless. An unreadable day map should
be preserved. This reconciliation has its own verification and cannot
be part of the IndexedDB commit.

That checkpoint left a verified completion read path as the next
prerequisite before enabling either Done writer.

## Verified completion reads

The completion-read fixture explicitly selects synthetic Task `t1` and
stores a separate scoring selection marker. At fixture creation only,
V2 seals the seeded rewards and writes matching completion rows. A
single IndexedDB read verifies those rows, the Task, its mutation
receipts, and the owner metadata. A lost owner marker by itself leaves
the separate scoring hold in place. This proof relies on the current
synthetic pages and does not extend to old clients or total storage loss.

Home's day snapshot and score summaries, Today's checked row, Game's
player scores, and the shared `syncYouMatchups` calculation use the
verified completions. The reader replaces just the selected Task's
legacy rewards and includes the latest unrelated V1 completions and
pending journals. An existing legacy reward must have a corresponding
seeded ID and timestamp. The fixture verifies that a stale 5-point row
contributes only its authoritative 12.75 points, a second Task adds
3 points, and past days preserve -2.25 and 0. Home and Game round
15.75 to 15.8 for display.

The real Matchups generation control runs under fresh verification.
The final V1 snapshot check rejects score changes outside that scope and
checks the completion source immediately before replacement. This
fixture saves the affected matchup synchronously inside its verified
action, since the ordinary deferred toolbar write can outlive that
verification. The V1 matchup snapshot carries calculated scores and
keeps its original completion records. An affected write is refused
if a receipt or completion is missing or corrupt, the owner evidence
is lost, a read is interrupted, a recovery hold exists, or a legacy
Task edit or malformed journal makes the source untrustworthy.

Done remains paused. This milestone established seeded completion
reads. The later rollback milestone below adds completion transfer.

The full run passed 59 of 60 browser cases. All 10 new scoring cases,
19 component browser cases, and 264 scoped regressions passed. The
one full-run failure was the existing intermittent Inbox assertion
that the compacted edit must be durable before navigation. The
isolated Inbox rerun passed. The assertion remains unchanged.

## Restart-safe Today-list cleanup

The current Today list stores Tasks, order, notes, and Habit selections
in separate maps keyed by local day. Home also recognizes an older
flat format. In the isolated scoring fixture, Home and Today acquire
the same browser lock. They freshly verify the seeded rewards and
the V2 Task receipt chain, then read the latest Today list. Cleanup
removes only `t1` and `task:t1` from days with a verified completion,
including the matching flat list if present. Unrelated rows, dates and
opaque fields stay in the original record.

The verified completion is the replay instruction. If Chromium
interrupts before the write, the original entries still need cleanup.
If the write already happened, replay finds them absent and skips the
write. The code checks the source bytes immediately before replacement
and verifies the saved bytes afterward. Unreadable data or a missing
lock pauses the operation and preserves the source.

Today shows the verified checked row independently of its active list,
including while the lock is busy. The scoped render computes automatic
due-Task visibility in memory so it cannot re-add an active entry during
render. Explicit Today edits use the same lock and apply to the latest
record. An obsolete drag order is refused. Clear Done and removing a
checked row can dismiss the verified display by completion ID with no
effect on its reward or active membership.

The lock coordinates the current synthetic writers. It cannot fence
older clients, and the IndexedDB verification and localStorage update
remain separate operations. Live V2 Done stays paused. The next
prerequisite is verified rollback of both the Task and its completion
history into a fresh synthetic V1 profile.

The full run passed 64 of 65 browser cases, including all five
Today-list cases. All 19 component cases and 319 scoped regressions
passed. The full run's only failure was the intermittent Inbox display
timeout after its storage checks had passed. All nine cases in the
focused rerun passed, including Inbox, scoring, and the Today-list
restart and competing-edit checks.

## Verified Task and completion rollback

The detached checkpoint checks the selected Task against its V2
receipts and checks every seeded completion against its sealed record.
It replaces the selected Task and its rewards in a copy of the current
V1 snapshot. It preserves each completion ID, timestamp, earned value,
and metadata. The original and current V1 strings, including backup
slots and pending journal bytes, stay in the checkpoint. V1 replays
those journals when it opens the copy. A pending deletion of an
unrelated completion still takes effect. A tombstone or competing
record for a V2 completion ID stops the checkpoint.

The checkpoint carries V1 IndexedDB backups and image bytes, including
orphan images. Unreadable data, unsupported database layouts, and
changing source evidence cause a refusal. The final V2 transaction
checks the Task, receipts, completions, and current V1 bytes before
recording the checkpoint checksum and freezing V2. The legacy
databases are read twice as separate operations.

The loopback importer accepts only an empty disposable profile. It
checks the reopened package's checksum, restores its records, and
compares all restored data and the effective V1 reader output. An
interrupted import keeps a recovery hold and requires a fresh
disposable profile for retry. The source can reproduce the same frozen
checkpoint as long as the source evidence still matches. Source V1
bytes and V2 Task and reward records stay intact.

The browser checks use ordinary V1 Home, Today, Game, and Matchups,
including a normal Home save and a Chromium restart. The recurring
fixture preserves 12.75, -2.25, and 0 earned points even after the Task
is edited to 19 points. The one-off fixture preserves its completed
state and original reward. The saved matchups use the same totals as
Game and Home. Both Home and Today still hold V2 Done in the source
experiment. The next step is to prove that the V2 write transaction can
enforce one reward per Task per local day across both controls and
return the original receipt on retry.

Chromium passed 75 of 76 full Home cases, including all 11 new
rollback cases. All 19 component cases and 319 scoped regressions
passed. The only full-run failure was `seed_source_changed` while
setting up the existing shared Done admission test. The same test
failed with the same error on the starting commit, `61c84013`, and
passed in the focused rerun of this change. The intermittent Inbox
display check passed in both runs on this change. Both assertions
remain in place.

## Atomic synthetic Task completion

Only the explicitly write-enabled loopback fixture can run the
transaction, and it owns only Task `t1`. The existing Home and Today
Done controls still refuse that Task. The harness calls the transaction
directly from both pages.

One strict IndexedDB transaction verifies the Task and its history,
checks the expected Task revision, and writes the updated Task, earned
reward, receipt, and revision. The completion store has a unique key
for the Task and local day. Seeded historical rewards also reserve
their days. Home and Today requests with different action IDs compete
for one reward, even with browser locks unavailable. A retry with the
original intent retrieves the original receipt after verifying the
committed data. On the same day, the initiating surface can recover its
committed intent from IndexedDB after losing its response.

The reward records the points from the verified Task revision and
keeps that value when the Task is edited later. One-off Tasks close
with a completion timestamp. Recurring Tasks advance from the due
date, clear postponement, and remain active. The fixture uses the
same local midnight as Home and Today. A timezone change pauses the
fixture, and metric-derived rewards are refused because they follow
a separate scoring formula.

Home, Today, Game, and Matchups read the same checked rewards. The
receipt verifier replays the original Task revision and checks that
its completion and revision match the persisted records. Scoring
writes and Today-list cleanup use fresh proof while a competing V2
write is excluded. Today-list persistence still runs separately in
localStorage and can replay after restart. The detached rollback
checkpoint carries the new Task and reward to ordinary V1 once.

All 20 transaction tests, 19 component tests, and 319 scoped
regressions passed. The full browser run passed 75 of the 76 existing
cases. The one failure was the previously reproduced Today setup

The final 20-case run includes the corrected timezone fault injection.

## How the integration works

- The loopback harness explicitly selects a single synthetic Task and checks the
  fixture marker against V2 metadata. The Home card and Critical Tasks display use
  a separate view verified against the durable V2 receipt chain. The card waits for
  that read at startup and stays withheld if V2 cannot be verified. Lifecycle
  refresh rereads V2 even when the V1 revision did not change.
- Home keeps the V1 backing state and storage cache on their legacy values. The
  V2 display is not passed to ordinary snapshot, journal, maintenance, or backup
  writers. Both the original localStorage and native IndexedDB boot paths still run.
- V2 checks the canonical owned Task, its linked completions, its pending Task
  journal evidence, the legacy generation, and the existing recovery holds. The
  read and transaction checks refuse genuine conflicts and unreadable evidence.
  Unrelated Task compaction and verified-secondary diagnostics can change without
  disabling V2 edits. The component experiment retains its original full-source check.
- The Task-only rollback freezes V2 at the verified revision, reads the current legacy
  snapshot, and inserts only the verified owned Task into a detached candidate. A fresh
  synthetic V1 profile opens at the latest V2 date and keeps the latest unrelated
  Task edit. Original/current legacy strings and receipts remain archived. The
  source images and journals are left in place. This checkpoint exercises Task
  compatibility. PR #1004 retains the separate full storage-transfer format.

## Evidence and limits

The loopback tests run checked-in Home HTML and its real controls, Notes
navigation and the core script order derived from `_worker.js`. The service
provides static assets and the bundle without Cloudflare HTML rewriting. Test
profiles use only synthetic data and block external browser requests.

The acceptance cases assert the actual Task card date after each path. They track
first paint on reload to catch a temporary stale date. The tests also cover quota,
before and after commit interruption, stale V2 and competing V1 edits, malformed
journals, missing receipts, and the detached rollback checkpoint. The preservation
checks compare the unrelated Task, Habit, Flex, Game, Gold, Projects, Notes,
unknown Task fields and raw keys, quarantine evidence, and exact image bytes.
Habit comparisons omit three named derived display counters that ordinary Home
adds on save. The Inbox comparisons use an actual generated notification, and the dedicated
cold-start test requires that the ordinary startup snapshot save preserve it.

The experiment covers +1 Day and edits to Title, Importance, Tags,
and Points on one synthetic Task. The
installed iPhone handoff, real-data transfer, and old-client transition
requirements remain unresolved. Ordinary V1 storage and UI paths retain
their existing behavior with the experiment disabled.
